# CiFi MVP Audit Against Research

Date: 2026-03-28

Reference: `C:\Users\Shadow\Downloads\deep-research-report.md`

## Practical assumption

I am treating the research report as the target product direction and the current repo as a prototype that should be steered toward that MVP with the smallest reasonable refactor, not a greenfield rewrite.

## Brief architecture assessment

The current app is a static local-first web shell with one large `app.js` file, one `index.html` shell, browser `localStorage` persistence, a versioned snapshot JSON, and light smoke tests. That foundation matches the desired delivery model reasonably well:

- Local-first storage already exists via `loadStoredJson` / `saveStoredJson` in `app.js`.
- A shared profile concept already exists via `state.profile`.
- A separate game-data snapshot already exists via `data/game-data.snapshot.v1.json`.
- The UI is already split into route-like sections in `index.html`.

The problem is product fit, not app-shell existence. The implemented modules are misaligned with the recommended MVP:

- `Ship Optimizer` is the most developed module and uses a real-ish calibration model in `buildShipConfig`, `getInstallBaseMultiplier`, and the install editor flow.
- `Progression` is placeholder scoring over a generic `progressionActions` table.
- `Gem Nodes` is a placeholder optimizer around generic gem-node rows.
- `Research` is not a user-facing optimizer; it is a research-notes display surface.
- `Data` is built around importing app-owned snapshot tables, not player-state onboarding.
- Screenshot OCR is present as a scaffold even though the research explicitly says OCR should not be part of MVP unless nearly free.

The repo’s own docs already admit this. `README.md` says the optimizer math and sample data are still prototype placeholders, and `docs/spec-reevaluation.md` says the current prototype uses placeholder data and categories and should be re-centered on real CiFi systems.

## What product is actually implemented today

Today this repo implements a local browser app with these concrete capabilities:

1. Shared profile form
   - Implemented in `index.html` profile page and `collectProfileForm` / `fillProfileForm` in `app.js`.
   - Stores generic values like `power`, `speed`, `cargo`, `gems`, `tokens`, `relics`, `gemDust`, `traitSphereCount`, and `mechParts`.

2. Persistent ship loadout editor
   - Implemented across `buildShipConfig`, ship rendering functions, `getBestNextInstall`, `rankShipTargets`, and `getInstallBaseMultiplier` in `app.js`.
   - This is the only module with meaningful domain-specific mechanics and a large calibration surface.

3. Snapshot import/export workspace
   - Implemented in `previewImport`, `normalizeImportRow`, `applyImportPreview`, and `exportSnapshot`.
   - Imports app dataset rows into `shipLoadouts`, `progressionActions`, `gemNodes`, `validationCases`, and `researchTracks`.

4. Generic progression scorer
   - Implemented in `runProgressionOptimization`.
   - Scores rows using `baseValue * affordability * urgency`.
   - Not tied to shard milestones, diamond/token planning, or loop-reset guidance.

5. Generic gem-node scorer
   - Implemented in `runGemOptimization`.
   - Scores rows using `value / cost`, level catch-up, and a budget mode.
   - This does not map cleanly to the recommended MVP.

6. Validation dashboard
   - Implemented in `runValidationCases`.
   - Validates current outputs against snapshot-defined expected winners.
   - Useful pattern, but currently validates placeholder behaviors rather than real player-facing recommendations.

7. OCR scaffold for generator manual values
   - Implemented in `parseGeneratorOcrImages`, `applyGeneratorOcrPreview`, and `scripts/generator-ocr.py`.
   - Feels exploratory rather than necessary for the MVP.

8. Research-notes panel
   - Implemented by rendering `snapshot.researchTracks`.
   - This is planning metadata, not an MVP feature.

## Comparison to target MVP

### What already exists and is reusable

- Local-first web app shell: keep.
- Shared persistence model via `localStorage`: keep.
- Single-page route structure in `index.html`: keep.
- Split between player state and snapshot data: keep, but tighten the boundary.
- Validation/golden-check pattern: keep.
- Some ship/player-state calibration concepts in `buildShipConfig`: partially reusable as future module state.

### What should be removed or deprioritized

- Generic `Gem Nodes` MVP surface: cut or defer.
- `Research` page as free-form research tracks: defer.
- Broad snapshot import as the primary onboarding path: deprioritize in favor of guided/manual profile import.
- OCR workflow: defer behind an experimental flag or hide entirely for MVP.
- Generic `progressionActions` table as a recommendation system: cut and replace with explicit module outputs.

### What is missing but essential

- Canonical unified `PlayerProfile` schema aligned to supported systems.
- Stage-aware guided/manual import flow.
- Explicit shard milestone optimizer module.
- Explicit diamond/token spend planner.
- Loop-reset guardrails and warnings.
- Central recommendation ranking layer that merges module candidates.
- Explanation layer with `why now`, assumptions, and confidence.
- Local profile export/import for the unified profile itself, not just snapshot exports.

### Where the current architecture fights the product direction

- `app.js` mixes UI rendering, persistence, import logic, scoring, ship formulas, and OCR in one file. That makes modular expansion harder than it needs to be.
- The primary import abstraction is dataset import into a game snapshot, not player profile acquisition. That is the wrong first-mile workflow for the MVP.
- Recommendation generation is snapshot-table driven, not module-driven. That encourages generic rows instead of explainable account-specific actions.
- The profile schema is a mixed bag of real and placeholder fields, so it is not a trustworthy single source of truth.
- The app currently gives equal product weight to ship optimization, gem nodes, research notes, validation, and OCR. The research MVP needs a much narrower center of gravity.

## Import approach evaluation

## How player state is modeled today

There are effectively two player-state models today:

1. `state.profile`
   - Lightweight shared profile based on `DEMO_PROFILE` in `app.js`.
   - Includes generic fields like `power`, `speed`, `cargo`, `relics`, `gemDust`, `traitSphereCount`, and `mechParts`.
   - This is presented as the cross-module player profile.

2. `state.shipConfig.playerState`
   - Rich ship-specific calibration built in `buildShipConfig`.
   - Includes grouped state for `academyGears`, `innovation`, `generators`, `techLevels`, `zagreus`, `hephaestus`, `demeter`, `koios`, `zeus`, `crew`, and `technical`.
   - This is the only place the app actually models stage-specific CiFi state with meaningful detail.

That split is the core issue: the nominal unified profile is too generic, while the real domain data lives inside ship-specific config.

## Does it support a unified profile?

Partially, but not cleanly.

Why it helps:

- The app already assumes a single active profile in `state.profile`.
- The ship config already contains many of the real progression slices a future unified profile would need.

Why it fails:

- The canonical player source of truth is ambiguous: some values live in `profile`, others in `shipConfig.playerState`.
- Import and persistence are separate between the profile and ship config.
- The visible profile schema is not module-oriented around the MVP systems.

## Minimum changes needed for guided/manual import first

Smallest viable path:

1. Introduce a canonical `PlayerProfile` object at the top level of app state.
   - Add it in `app.js` near the current `DEMO_PROFILE` / state initialization.
   - Treat current `state.profile` as the seed for `playerProfile`.

2. Move `shipConfig.playerState` under the canonical profile.
   - New shape should be conceptually:
   - `playerProfile.meta`
   - `playerProfile.stage`
   - `playerProfile.resources`
   - `playerProfile.systems.loop`
   - `playerProfile.systems.shards`
   - `playerProfile.systems.spend`
   - `playerProfile.systems.ship`

3. Replace the current `Profile` page with guided/manual import for MVP-supported systems.
   - Ask only for:
   - stage or highest ship unlocked
   - loop-reset context needed for guardrails
   - shard milestone levels and timing inputs
   - diamond/token balances, rates, and owned spend targets

4. Add explicit profile export/import separate from snapshot export/import.
   - Reuse the current browser download approach from `exportSnapshot`.

5. Keep dataset import only for static game data and internal calibration, not as the primary user import surface.

## Recommendation engine evaluation

## What engine exists today?

It is mixed, but mostly shallow scoring:

- `runShipOptimization` is a scoring-based ranking over snapshot-defined loadout presets.
- The ship editor itself has formula-driven install evaluation via `getInstallGain`, `getBestNextInstall`, and `getInstallBaseMultiplier`.
- `runProgressionOptimization` is plain scoring-based.
- `runGemOptimization` is plain ROI scoring-based.
- `runValidationCases` is benchmark comparison, not recommendation logic.

So the repo today is best described as:

- mixed scoring-based prototype
- with one specialized formula-heavy ship sub-engine
- and no central recommendation abstraction

It is not simulation-first and not a coherent rule engine.

## Can it support explainable recommendations?

Yes, but only after the recommendation surface is restructured.

Why:

- Current recommendation cards already accept `title`, `subtitle`, `confidence`, and `notes`.
- That gives a workable UI slot for explanation content.
- The engine outputs are already candidate lists that can be merged and ranked.

What is missing:

- A shared `RecommendationAction` model.
- Structured `whyNow`, `benefitSummary`, `costSummary`, `assumptions`, and `warnings`.
- Module attribution and comparable score normalization across modules.

## What should be the first MVP engine?

For the MVP, use a hybrid:

1. Rule-based engine for loop-reset guardrails and warnings.
   - This is the cleanest way to express “spend before reset”, “you are about to lose value”, or “this looks like a short-run profile”.

2. ROI / scoring engine for shard milestone and diamond/token recommendations.
   - This fits the research recommendation and matches the repo’s existing scoring style.
   - It is simpler to ship and explain than a global simulator.

Do not start with:

- broad simulation of everything
- full multi-system optimizer
- late-game global search

## Where to add module boundaries, ranking, and explanations

Smallest high-leverage structure:

- `modules/shards.js`
  - `enumerateShardActions(profile, gameData)`
- `modules/spend.js`
  - `enumerateSpendActions(profile, gameData)`
- `modules/loopGuardrails.js`
  - `enumerateLoopWarnings(profile)`
- `modules/recommendations.js`
  - `rankRecommendations(actions, objective)`
- `modules/explanations.js`
  - `renderRecommendationExplanation(action, profile)`

If you want the absolute smallest first step without a folder refactor, create those as grouped functions inside `app.js`, then extract later.

Shared action shape:

```js
{
  id: "shards-next-threshold-foo",
  module: "shards",
  kind: "upgrade" | "warning",
  title: "Push Milestone X to 25",
  score: 0,
  confidence: 0.82,
  cost: { resource: "shards", amount: 12345 },
  eta: { seconds: 5400 },
  benefit: ["Unlocks threshold bonus", "+x% shard gain"],
  whyNow: ["You are 2 levels from a breakpoint", "Shards are loop-reset sensitive"],
  assumptions: ["Ticks/op based on manual input"],
  warnings: []
}
```

## Concrete implementation plan

## Phase 0: cleanup / refactor

1. Freeze prototype-only surfaces behind a lower priority.
   - Remove or hide `Gem Nodes` and `Research` from primary nav in `index.html`.
   - Hide OCR from the default flow.

2. Introduce canonical `PlayerProfile`.
   - Add schema and migration helpers in `app.js`.
   - Move ship player-state under the unified profile.

3. Separate static game data from user data more clearly.
   - Keep `data/game-data.snapshot.v1.json`, but split it into supported-module slices or at least rename datasets away from placeholder categories.

4. Replace generic naming.
   - Remove placeholder `progressionActions` and `gemNodes` terminology from UI and data model.

5. Add a minimal recommendation action contract.
   - Needed before building the unified recommendation feed.

## Phase 1: MVP ship path

1. Guided/manual import
   - Convert the `Profile` page into a stage-aware onboarding flow for supported systems.
   - Add profile export/import.

2. Shard milestone optimizer
   - Use the next real module after ships because it is central to the research MVP and highly explainable.
   - Add milestone levels, timing inputs, threshold-aware ranking, and ETA output.

3. Diamond/token spend planner
   - Build a bounded planner around current balances, income rates, and upgrade choices.
   - Output best-next-buy plus ETA.

4. Loop-reset guardrails
   - Add warnings and “before you reset” checks.
   - Keep this rule-based and stage-aware.

5. Unified recommendation feed
   - Replace overview highlights with merged outputs from shard, spend, and loop modules.
   - Add `why this now` output directly on the cards.

6. Validation fixtures
   - Replace snapshot winner tests with recommendation fixtures for real module cases.

## Phase 2: post-MVP expansion

1. Expand ship optimizer integration
   - Reconnect ship recommendations into the unified feed only after the MVP modules are stable.

2. Add research planning
   - Only after the base profile and recommendation engine are stable.

3. Add academy / Zeus module
   - Useful, but not needed for first value.

4. Revisit OCR or save parsing
   - Only after guided/manual import is clearly insufficient.

5. Consider advanced late-game systems
   - Keep explicit confidence flags for uncertain formulas.
